# GeoDNS на своих VPS

На двух существующих VPS работает PowerDNS Authoritative 5.1 с одинаковой зоной и локальной DB-IP Country Lite. Внешнего DNS-хостинга, аккаунта или подписки нет.

Оба NS применяют **одно правило**: российская подсеть получает origin, остальные и неизвестные адреса — KZ. Нельзя делать «первый NS всегда RU, второй всегда KZ»: выбор NS не определяет страну посетителя. У основного домена и www одинаковая маршрутизация; HTTPS www перенаправляется на основной адрес с сохранением пути.

Приложение, фотографии, SQLite и TLS остаются на origin; KZ передаёт HTTPS по TCP, как описано в [edge-proxy.md](edge-proxy.md).

## Текущее состояние

Собственное делегирование уже действует: ns1.dogovorimsya.online и ns2.dogovorimsya.online. На проверке 7 ноября оба отвечали serial 2026110602, межсерверная проверка KZ-NS с RU/GB ECS вернула origin/KZ. Службы обоих NS работают. Это не гарантия, что каждый российский браузер получает origin: 7 ноября конкретный Mac с RU HTTP-выходом разрешал домен в KZ и терял большой ответ. Результаты и следующий разбор — [status.md](status.md).

## Подготовка

[render.py](../deploy/geodns/render.py) создаёт зону и конфиг без Python-зависимостей:

```sh
python3 deploy/geodns/render.py \
  --domain couple.example --origin 192.0.2.10 --edge 192.0.2.30 \
  --output artifacts/geodns/config --serial 2026110601
```

Адреса выше условные. В config/country.mmdb положить [DB-IP Country Lite](https://db-ip.com/db/download/ip-to-country-lite), проверив распакованный файл по опубликованной сумме. Это бесплатный файл по CC BY 4.0, не API: запросы посетителей обрабатываются локально. Источник указан в [ATTRIBUTION.md](../deploy/geodns/ATTRIBUTION.md) и TXT _geodns.

Реальные конфиги, .env, MMDB и резервные копии не коммитятся. На серверах отдельный каталог /home/codex/apps/dogovorimsya-dns. Serial, зона и MMDB должны совпадать на обоих узлах. У географических ответов TTL 60, у NS и адресов ns1/ns2 — 3600.

[compose.yaml](../deploy/geodns/compose.yaml) запускает отдельный контейнер с закреплённым digest. Публичные TCP/UDP 53 передаются на непривилегированный 1053. Процесс непривилегированный, filesystem read-only, лимит 128 МБ.

[install-native.sh](../deploy/geodns/install-native.sh) предназначен для владельца Ubuntu 22.04/24.04 с отдельным разрешением на root. Он добавляет официальный репозиторий 5.1 с отдельным signing key, устанавливает pdns-server и pdns-backend-geoip, маскирует неиспользуемую стандартную службу и создаёт dogovorimsya-dns.service. Другие демоны через needrestart автоматически не перезапускаются.

Native-процесс работает от codex с CAP_NET_BIND_SERVICE. Home скрыт в mount namespace; виден только read-only каталог конфигурации. DNS слушает переданный публичный IPv4, сохраняя systemd-resolved на loopback. При активном UFW добавляются только UDP/TCP 53 для этого IPv4; сам UFW не включается. Установщик NS у регистратора не меняет.

## Проверка до делегирования

Каждый публичный NS проверять с другого VPS по UDP и TCP:

```sh
dig @192.0.2.10 couple.example SOA +time=3 +tries=1 +short
dig @192.0.2.10 couple.example A +subnet=85.198.104.0/24 +time=3 +tries=1 +short
dig @192.0.2.10 couple.example A +tcp +subnet=62.164.142.0/24 +time=3 +tries=1 +short
```

Повторить для второго NS, www и IPv6-подсетей. Сверить SOA/NS, отсутствие неподдерживаемого AAAA, NXDOMAIN отсутствующего имени, REFUSED для чужой зоны и отказ AXFR. Проверить запросы без ECS из RU и KZ.

Сервер только авторитетный: без рекурсии, DNS Update, AXFR, API и веб-панели. Кэши ответов отключены, чтобы решения по разным подсетям не смешивались. Контрольная команда Authoritative — **pdns_control rping**, не ping.

На Mac даже dig @IP возвращал старые ответы с TTL исходной зоны. Такой ответ не подтверждает работу нашего NS: сверять serial и содержимое. Предварительные внешние проверки выполнялись по SSH между VPS. Сайт проверять напрямую и через Happ, каждый раз сначала получая внешний IP Cloudflare.

## REG.RU

Для действующего домена эти шаги уже выполнены; это процедура первоначального подключения или согласованного восстановления, не текущая задача. После проверки обоих публичных NS:

1. «DNS-серверы и управление зоной» → изменение DNS-серверов → «Свой список DNS-серверов».
2. ns1.<домен> с IPv4 origin и ns2.<домен> с IPv4 KZ.
3. В появившихся полях указать IP — это glue-записи для NS внутри своего домена.
4. Сохранить, проверить родительское делегирование, оба NS и публичные резолверы.

Регистратор остаётся прежним. Все исходные записи зоны перенести до переключения; два обычных A-адреса географическое правило не создают. Проверить отсутствие неожиданного DS, чтобы не сломать DNSSEC-валидацию новой зоны.

Новый TTL 60 не сокращает задним числом старый TTL или кэш делегирования. Проверять реальные ответы, не обещать мгновенный переход.

## Ограничения и обслуживание

При EDNS Client Subnet используется переданная подсеть, иначе — адрес резолвера. Страна DNS может отличаться от выхода VPN/HTTP-прокси. Проверять конкретный клиент; GeoDNS не исправляет потери выбранного маршрута.

DB-IP обновляется ежемесячно. Обновление через staging: скачать и проверить файл, протестировать отдельным непривилегированным PowerDNS, атомарно заменить на обоих узлах и выполнить pdns_control reload. При ошибке вернуть прежний файл и повторить reload. Автоматический updater пока не установлен.

Зону менять одинаково на обоих NS с повышением serial; поддерживать native-пакеты и Docker digest согласованно. Откат — прежние NS регистратора и сохранённые записи. Не выключать свои NS, пока старое делегирование ещё используется. Данные приложения не трогать.
