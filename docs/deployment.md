# Развёртывание, резервные копии и откат

Это runbook **существующей** установки. Приложение уже развёрнуто; не начинать с настройки нового сервера, домена или первого аккаунта. Состояние и последний код — [status.md](status.md). Новый чистый стенд описан отдельно в конце.

| Что | Где |

| SSH | `ssh ha-vps`, пользователь `codex`; edge/DNS — `ssh kz-bot` |
| Клон приложения | `/home/codex/apps/dogovorimsya`, ветка `codex/mvp` |

## Доступ и самостоятельная работа агента с Mac

На Mac владельца настроены aliases `ha-vps` и `kz-bot`; оба подключают пользователя codex по имеющейся ключевой авторизации. Это действующий доступ агента, а не предложение запросить его в будущем. Пользователь разрешил самостоятельно разворачивать обновления проекта и мониторить оба сервера в рамках задач проекта и прав codex.

Можно получать код из Git, собирать приложение, делать бэкапы, обновлять его контейнер, проверять `docker ps`, `docker compose ps/logs`, healthcheck, доступные `systemctl status/is-active` и журналы, порты и HTTP/DNS. Не просить владельца выполнять обычные доступные агенту команды или повторно подтверждать такой деплой. При этом не выводить секреты из логов/конфигов и не затрагивать чужие приложения.

Проверка подключения с этого Mac при необходимости:

```sh
ssh -o BatchMode=yes -o ConnectTimeout=10 ha-vps 'id -un'
ssh -o BatchMode=yes -o ConnectTimeout=10 kz-bot 'id -un'
```

Ожидаемый пользователь — codex. На другом компьютере сначала проверить наличие SSH-конфигурации, не считать эти aliases универсальными. Ключи/пароли не просить присылать в чат. Root/sudo требуют отдельного разрешения на конкретное действие; доступ по SSH его не заменяет. Для обычного мониторинга и обновления app от codex отдельное подтверждение не требуется.

## Чтение текущего состояния

```sh
ssh ha-vps
cd /home/codex/apps/dogovorimsya

dc() {
  docker compose --env-file deploy/.env -f compose.yaml -f deploy/compose.proxy.yaml "$@"
}

git status -sb
git log -1 --oneline
dc ps

docker exec dogovorimsya-app-1 node --input-type=module -e '
import { DatabaseSync } from "node:sqlite";
const db = new DatabaseSync("/app/data/private/app.db", { readOnly: true });
console.log({ node: process.version, schema: db.prepare("PRAGMA user_version").get().user_version });
db.close();
'
```

Git HEAD показывает checkout, не обязательно код в работающем образе. Для сравнения релизов сверять также образ и ресурсы внутри контейнера. Не читать личные строки или секреты для диагностики версии. `openDatabase` приложения запускает миграции; для чтения не вызывать её.

## Обновление только приложения

Для правки документации достаточно обновить Git; контейнер не пересобирать и не перезапускать. Для изменения исполняемого кода:

1. Убедиться, что checkout чистый, получить и проверить нужный коммит без потери локальных изменений.
2. **До build** сохранить отдельный тег предыдущего рабочего образа. Это нужно для отката: после замены latest старый образ может оказаться недоступным по digest из container inspect. Сверить, что тегируемый образ соответствует действующему релизу.
3. Собрать кандидата. Dockerfile сам выполняет тесты, TypeScript и сборку. Сборка не должна монтировать живую БД.
4. Остановить только app, сделать и проверить полную приватную копию тома. При сбое копирования запустить прежний app.
5. Пересоздать только app с уже собранным образом. Не использовать down -v и не перезапускать Caddy, DNS или другие приложения.
6. Проверить healthy, схему, сохранность прежних данных/файлов, HTTPS, закрытые API и полный клиентский скрипт. Не публиковать фиктивные отзывы или push в личной базе.

Подготовка в той же SSH-сессии, после проверки чистого checkout:

```sh
git fetch origin
git pull --ff-only origin codex/mvp

release_stamp=$(date -u +%Y%m%dT%H%M%SZ)
rollback_image="dogovorimsya-app:before-$release_stamp"
docker image inspect dogovorimsya-app >/dev/null
docker tag dogovorimsya-app "$rollback_image"
dc build app
```

При локальных изменениях остановиться на разборе их происхождения; не применять reset --hard или принудительный pull. Ветка main содержит актуальный проект, но текущий production-клон не надо самовольно переключать на другую ветку.

### Согласованная копия и применение

Следующий блок выполняется после успешной сборки и использует сохранённый старый образ только для tar. Все данные остаются на сервере, helper читает том read-only, работает от непривилегированного пользователя образа и не запускает приложение/миграции.

```sh
(
  set -eu
  umask 077
  backup_dir="backups/before-$release_stamp"
  mkdir -p "$backup_dir"
  chmod 700 backups "$backup_dir"
  before_switch=1
  restart_previous() {
    if [ "$before_switch" -eq 1 ]; then
      dc start app
    fi
  }
  trap restart_previous EXIT

  printf '%s\n' "$rollback_image" > "$backup_dir/rollback-image.txt"
  git rev-parse HEAD > "$backup_dir/candidate-commit.txt"
  dc stop app
  docker run --rm --network none \
    --mount type=volume,src=dogovorimsya_journal_data,dst=/app/data,readonly \
    --entrypoint tar "$rollback_image" -czf - -C /app/data . \
    > "$backup_dir/journal.tar.gz.tmp"
  tar -tzf "$backup_dir/journal.tar.gz.tmp" > "$backup_dir/archive-files.txt"
  mv "$backup_dir/journal.tar.gz.tmp" "$backup_dir/journal.tar.gz"

  before_switch=0
  dc up -d --no-build --no-deps app
)

dc ps
```

Trap запускает прежний контейнер при ошибке в фазе копирования. После начала переключения не выполнять автоматический откат схемы: при ошибке up/healthy разобраться в состоянии контейнера и совместимости сохранённого образа. Не считать один успешный up подтверждением здоровья.

Архив должен содержать `private/app.db`, `private/uploads/` и `private/push-vapid.json`, а также WAL/SHM, если они остались. Сохраняется весь том; копирование только app.db при работающем WAL не является согласованным бэкапом. Содержимое архивов и списки личных файлов не публиковать. Для проверки SQLite из read-only-архива распаковать её в отдельный приватный доступный для записи каталог: WAL-режиму может потребоваться создать SHM. Не исправлять это расширением прав живых данных.

Для миграции дополнительно сохранить контрольные значения по прежним колонкам таблиц и хеши медиа/VAPID. После запуска сравнить их, отдельно проверить новые поля и права. Файл SQLite побайтово меняется при миграции и не обязан иметь прежний SHA. Успешный такой перенос v7 → v8 зафиксирован в [status.md](status.md).

## Внешняя проверка

Проверить `/api/status` → `{"demo":false}`, приватный `/api/bootstrap` без cookie → 401, HTML и полный скрипт из его src. Сравнить распакованные байты/SHA-256 с ресурсом внутри контейнера. Проверить редиректы HTTP и www, действующий сертификат. Не использовать curl -k.

На Mac проверять прямой путь и HTTP Happ `127.0.0.1:10809`; **перед каждым запросом сайта** сначала Cloudflare `/cdn-cgi/trace` с теми же proxy/no-proxy параметрами. Примеры и диагностика — [edge-proxy.md](edge-proxy.md). Есть воспроизводимая проблема прямого RU-маршрута через KZ; HTTP 200 без полного тела не означает успешную загрузку.

Личные операции проверить на локальном демо/временной базе. Физическую установку и получение уведомления проверяет владелец на iPhone. После функционального обновления уже открытая PWA может сохранять прежний JavaScript до закрытия/повторного открытия; обновление ленты не заменяет загрузку новой версии приложения.

## Откат

Сохранить тег и конфигурацию предыдущего образа **до** сборки. Проверить совместимость со схемой, которая уже успела запуститься. Старый код может не понимать новые поля и понижать user_version при открытии; простой перезапуск старого образа не является универсальным откатом миграции.

Для заведомо совместимого образа можно подготовить отдельный compose override с services.app.image, проверить итоговую конфигурацию, затем применить его вместе с обоими основными compose-файлами через up -d --no-build --no-deps app. Не менять образ других сервисов. Сохранённый тег/override хранить в приватной папке бэкапа.

Восстановление БД — отдельное решение с владельцем: после бэкапа могли появиться новые реальные записи. Нельзя автоматически затереть их старым архивом. Перед восстановлением сохранить также текущее состояние, остановить app и восстанавливать SQLite, uploads и VAPID согласованно. Не подменять сохранённые VAPID новыми ключами.

## Аккаунты и пароль

В текущем production аккаунты уже существуют. Bootstrap/setup для них не запускать; временный логин owner из примера не описывает действующий логин владельца.

Администратор выдаёт/отзывает код в «Доступ». Один код после регистрации восстанавливает только связанный аккаунт. Пароль меняется в профиле или по коду; администратор может сбросить пароль второго участника. Аварийный CLI-сброс — в интерактивном терминале, после проверки образа, схемы и резервной копии:

```sh
dc run --rm --no-deps app node build/scripts/accounts.js reset reviewer
```

Для второго профиля — recipient. Команда отзывает его сессии и подписки; реальный пароль вводит владелец, не аргументом и не в чате. В CLI reviewer/recipient — ключи профилей, не право редактировать все отзывы.

## Отдельный новый стенд

Это не инструкция перенастраивать действующий сайт. Compose явно задаёт project name dogovorimsya: другая папка клона сама по себе не изолирует данные. Новый стенд размещать на отдельном Docker-хосте либо заранее изолировать project name, тома, порты, сети и aliases; production override нельзя без адаптации подключать к тестовому контейнеру в той же сети Caddy.

Получить фактические параметры нового VPS, проверить порты, Docker, сеть и существующие сервисы. Создать приватный deploy/.env на основе [примера](../deploy/.env.example), указать домен/свободный loopback-порт и при необходимости PROXY_NETWORK для [override](../deploy/compose.proxy.yaml).

Собрать образ и только на пустом отдельном томе создать первого администратора через CLI setup либо bootstrap; второй аккаунт — по приглашению. При свободных 80/443 допустим встроенный Compose-профиль https; если Caddy уже есть, подключить только приложение к его сети и согласованно добавить отдельный маршрут с резервной копией конфигурации и validate/reload.

Для обычного нового домена без GeoDNS возможны стандартные DNS регистратора и A на свой VPS. **У действующего dogovorimsya.online уже свои GeoDNS**: его зону не менять как обычную A-запись REG.RU. Порядок делегирования/согласованного обновления обоих NS — [geodns.md](geodns.md), TCP edge — [edge-proxy.md](edge-proxy.md).

Автоматические бэкапы, перенос копий на независимый носитель и обновление MMDB в рамках проекта пока не настроены. Не заменять ими реальные уже сделанные ручные копии и не утверждать обратное без проверки.
