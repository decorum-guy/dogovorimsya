# Работа с «Договоримся»

Это работающая приватная PWA для пары. Начните с README.md и docs/status.md, затем docs/development.md. CLAUDE.md содержит краткий продуктовый и технический контекст. Проверяйте текущую ветку и локальные изменения перед правками; не перезаписывайте чужую работу.

- Сохранить название «Договоримся» и слоган «Оценки обсуждаются».
- Оба профиля создают оценки. Правка отзыва определяется author_id, админка — is_admin. role (`reviewer`/`recipient`) выбирает пул приветствий и оформление; это не право редактировать чужое.
- Не удалять и не «исправлять» согласованные фразы content/homeMessages.json без просьбы владельца. Гендерные формулировки, «вы» и мат оставлены намеренно. Не превращать шутки об апелляциях в новую систему функций.
- Не коммитить реальные данные пары, фотографии, учётные данные, коды, push-подписки, VAPID, .env, БД и архивы. Проверки интерфейса и API выполнять на демо/временной базе, не создавать фиктивные записи или тестовые push в production.
- Перед миграцией production сохранить весь приватный том: SQLite вместе с WAL при его наличии, uploads и push-vapid.json. Сохранить старые записи, версии, время, пароли, сессии, коды и отметки. Сама миграция не создаёт публикаций или уведомлений.
- Для изменения логики выполнить подходящие проверки, обычно npm test и npm run build. Для правки только документации проверить ссылки, команды и соответствие коду; пересборка и рестарт приложения ради текста не нужны.
- На VPS работать только от codex через согласованный SSH-доступ. Root/sudo — только после отдельного разрешения на конкретное действие. Старые разрешения на HAProxy/DNS не являются общим разрешением. Не менять и не перезапускать чужие сервисы.
- Сетевые проверки с Mac: напрямую и через HTTP-прокси Happ 127.0.0.1:10809. Перед каждым запросом сайта сначала Cloudflare /cdn-cgi/trace тем же маршрутом. Проверять полное тело скрипта и его SHA-256, не только HTTP 200. Не отключать TLS-валидацию.
- Фиксировать изменения поведения и фактический результат в соответствующей документации. Отделять наличие кода, факт деплоя и ручную проверку на устройстве. docs/status.md — текущая передача проекта; исторический аудит не заменяет её.

## Готовый доступ с рабочего Mac и полномочия агента

Если агент работает на Mac владельца, с которого ведётся эта разработка, SSH-доступ **уже настроен и ранее использован**:

| Сервер | Команда | Пользователь / назначение |
| --- | --- | --- |
| HA / origin | `ssh ha-vps` | `codex`, `95.142.42.46`: приложение, Docker, данные, Caddy и первый NS |
| KZ / edge | `ssh kz-bot` | `codex`, `38.244.134.21`: HAProxy и второй NS |

Владелец разрешил агенту самостоятельно подключаться к обоим серверам, разворачивать обновления проекта, собирать/пересоздавать его контейнер, делать приватные резервные копии, читать относящиеся к проекту логи, проверять процессы, healthcheck, Docker/Compose, доступные статусы systemd и сетевую доступность. По поручению на изменение проекта доводить работу до проверенного развёртывания в рамках этих прав; не просить повторное разрешение на обычный деплой или мониторинг от codex.

Сначала использовать существующие aliases и ключевую авторизацию, а не просить у владельца SSH-команду, пароль или приватный ключ заново. При сомнении проверить `ssh -G ha-vps` / `ssh -G kz-bot`, затем соединение с BatchMode и ограниченным временем подключения. На другой машине наличие aliases/ключей не гарантировано: проверить фактическую среду, при ошибке сообщить конкретную причину.

Эти полномочия действуют в задаче проекта и в пределах доступа codex. Они не разрешают root/sudo без отдельного согласования, изменение посторонних сервисов, опасное удаление данных или раскрытие секретов. Перед миграцией обязателен бэкап; сетевые изменения общих HAProxy/Caddy/DNS сначала подготовить и проверить, а при необходимости системных прав обратиться к владельцу за конкретным действием. Порядок — docs/deployment.md.
